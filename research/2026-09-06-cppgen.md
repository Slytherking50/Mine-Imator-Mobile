## Evidencia

### Pregunta 1 — subconjunto de GML soportado

- `CppGen/gml.json:2-34` → lista `keywords` completa: `break, case, constructor, continue, delete, div, do, else, enum, false, for, function, globalvar, id, if, mod, new, noone, object_index, other, repeat, return, self, static, switch, true, undefined, until, var, while, with`. Confirma lo que dice CLAUDE.md (`constructor`, `new`, `delete`, `static` → GML "moderno" con structs).
- `CppGen/Sources/CppGen.hpp:303-324` → `Statement::Type` soportados: `DeclarationList, StatementList, Declare, Macro, Enum, Call, Assign, If, While, DoUntil, For, Repeat, With, Switch, Break, Continue, Return, Delete, CustomCpp`. **No hay `Try`/`Catch`/`Throw`** — GML moderno tiene `try/catch/finally`, gml.json no los declara como keyword y no existe clase de Statement para ellos.
- `CppGen/Sources/Function.cpp:915-961` (`parseExprValue`) → expresiones primarias soportadas: `Number`, `String`, `ID` (accessor o `new`), `[ ... ]` (array literal), `( expr )`. **No hay caso para `{` como expresión** → no soporta struct-literal (`{a: 1, b: 2}`), ni función anónima/lambda como expresión (`function(){}` asignada a variable), ni interpolación de string (`$"texto {var}"`).
- `CppGen/Sources/Function.cpp:317-331` → `function` solo se parsea como declaración de script de nivel superior; si el siguiente token tras `)` es el identificador `constructor`, ese script se convierte en `Object` de tipo struct (`this->structObject = makeObject<Object>(this->name, true)`).
- `CppGen/Sources/Function.cpp:641-648` → `static` **solo es válido dentro de una función `constructor`** (para declarar un método estático tipo `static nombre = function(...) {...}`, patrón de "struct method" de GML moderno). Si aparece `static` fuera de un `constructor` (p. ej. `static x = 0;` como variable estática local, sintaxis GML moderna también válida), es error fatal: *"FATAL ERROR: Unexpected static in {0}:{1}."*
- `CppGen/Sources/Function.cpp:402-417` → soporta `#macro nombre expr` (`Token::Type::HashTag`) y un token especial `Token::Type::CppOnly`.
- `CppGen/Sources/GML.cpp:170-201` → el lexer reconoce dos comentarios mágicos: `/// CppSeparate <firma-C++>` (marca la función entera como implementada a mano en C++, solo se genera la firma) y `/// CppOnly <línea-C++>` (inyecta una línea de C++ literal dentro del cuerpo de la función). Uso real en el proyecto: `grep -rl "/// CppSeparate" GmProject --include=*.gml` → **71 archivos**; `/// CppOnly` → **1 archivo** (`GmProject/scripts/res_load_scenery/res_load_scenery.gml:179,231`, inyecta `#pragma OPENMP_FOR`).
- `CppGen/Sources/Statement.cpp:872-884` → `CustomCppStatement::writeCpp` hace `CodeWriter::write(this->cpp)` — **pega el texto tal cual**, sin ningún chequeo.
- `CppGen/Sources/CppGen.hpp:116-142` (`DataType::Type`) y `CppGen/Sources/DataType.cpp:85-158` → tipos reconocidos en `gml.json`: `int/IntType, real/RealType, string/StringType, reference<Obj>, vec/VecType, matrix/MatrixType, array/ArrType, list, anymap, intmap, stringmap, map, grid, stack, priority`. Cualquier otro string de tipo → *"FATAL ERROR: Unknown data type: {0}"* + `Environment::exit(1)` (`DataType.cpp:157-158`), y esto ocurre al parsear `gml.json`, antes de tocar `GmProject/`.
- `CppGen/gml.json:218` + conteo (`awk`) → sección `functions` con **382 entradas** (funciones built-in de GML con firma declarada: tipo de retorno, tipos de argumento, `varArgs`, `needScope`, `varCreateRef`).
- `CppGen/Sources/Accessor.cpp` (múltiples `else if (this->name == "...")` entre líneas 67-217 y 582-649) → además de la firma declarativa de `gml.json`, hay **~15 funciones con lógica de inferencia de tipo hardcodeada por nombre literal** en el propio C++ de CppGen: `new_obj`, `array_add`, `array`, `save_id_find`, `ds_int_map_create`, `ds_string_map_create`/`json_load`, `test`, `array_create`, `array_length`, `choose`/`max`/`min`, `ds_list_add`, `ds_map_find_first`/`_next`/`_value`, `ds_map_add`, `ds_stack_push`, `ds_grid_set`/`_get`, `ds_list_copy`/`ds_map_copy`, `shader_set_uniform_f`/`_i`.

### Pregunta 2 — manejo de función/construcción desconocida

Hay **cuatro comportamientos distintos** coexistiendo, no uno solo:

**(a) Error de sintaxis/lexer → fatal antes de tocar el proyecto o antes de escribir nada.**
- `CppGen/Sources/GML.cpp:349-353` → carácter no reconocido por el lexer → *"FATAL ERROR in {0}: Unexpected {0} token..."* + `exit(1)`.
- `CppGen/Sources/Function.cpp:358-372` (`nextToken`) → token inesperado durante el parseo → *"FATAL ERROR in {0}: Unexpected \"{0}\" at line {1}..."* + `exit(1)`.
- Estos ocurren dentro de `parseTokens()`, llamado en `Program.cpp:154-156`, **antes** de `resolveProject()` (línea 174) y muy antes de que empiece a escribirse cualquier archivo de salida (línea ~190 en adelante). Un error de sintaxis puro nunca deja `Generated/` a medio escribir.

**(b) Función/dato desconocido detectado durante `resolve()` → fatal, también antes de escribir.**
- `CppGen/Sources/Accessor.cpp:219-224` → llamada a algo que no es función de usuario ni built-in de `gml.json`, sin cadena previa → *"FATAL ERROR: Missing function {2} in {0}:{1}"* + `exit(1)`.
- `CppGen/Sources/Accessor.cpp:71-90` → argumentos inválidos a `new_obj()`/`array_add()` → fatal.
- Todo esto corre dentro de `resolveProject()` (`Program.cpp:174-181`), que también es anterior a la escritura de archivos.

**(c) Error detectado durante `toCpp()` (fase de escritura) → fatal a mitad de generar archivos — riesgo de salida parcial.**
- `CppGen/Sources/Accessor.cpp:808-811` (dentro de `Accessor::toCpp`, línea 455 en adelante) → *"FATAL ERROR: Invalid argument count for {2}..."* + `exit(1)`.
- Esto ocurre dentro del bucle de `Program.cpp:315-355` que escribe `Scripts1.cpp...ScriptsN.cpp`, **después** de que `Scripts.hpp`, `Globals.cpp` y potencialmente `Scripts1.cpp...Scripts(N-1).cpp` ya fueron escritos a disco (`CodeWriter::end` en `CodeWriter.cpp:55-76` hace `File::writeAllText` inmediatamente, archivo por archivo). Un `exit(1)` aquí deja `CppProject/Generated/` con una mezcla de archivos nuevos (los ya escritos) y archivos viejos (los que faltaban, incluidos `Assets.cpp`, `Objects*.cpp`, `AddGMLStrings.cpp`, que se generan después en el flujo de `Program.cpp:368-476`).

**(d) Un caso de "función desconocida" que imprime "FATAL ERROR" pero NO aborta y SÍ emite código.**
- `CppGen/Sources/Accessor.cpp:626-649` (dentro de `Accessor::toCpp`) → cuando se llama a una función de instancia que no se encuentra en ningún objeto del proyecto (`foundFuncAnywhere == false`) se imprime *"FATAL ERROR: Unknown function {2} in {0}:{1}"* (línea 641) **sin llamar a `Environment::exit(1)`** (no hay `exit` en ese bloque, a diferencia de los otros 14 sitios con el mismo prefijo "FATAL ERROR"). El código sigue y en la línea 644 genera igual `idFunc(previousInChain->toCpp(scope) + ", " + this->name)`, es decir, **emite una llamada a una función que CppGen sabe que no existe**. Esto tampoco se agrega a `Program::syntaxErrors`, así que ni siquiera afecta el código de salida del proceso (`main.cpp:9`: `return CppGen::Program::syntaxErrors.empty() ? 0 : 1;`). Es el único punto donde CppGen genera código potencialmente roto de forma silenciosa para el sistema de build (el error solo es visible si alguien lee el log de consola completo).

**(e) Construcciones/eventos no reconocidos por nombre → warning y omisión silenciosa (ni error ni excepción).**
- `CppGen/Sources/Object.cpp:16-60` → al construir un `Object` desde su carpeta, solo se reconocen 2 nombres de archivo de evento en general (`Create_0.gml` → constructor, `Destroy_0.gml` → destructor) y, únicamente si el objeto se llama literalmente `"app"` (línea 32), 4 más: `Draw_0.gml`, `Other_3.gml`, `Other_62.gml`, `Step_0.gml`. Cualquier otro archivo de evento cae en el `else` (líneas 51-59): *"WARNING: Unsupported event {0} in {1}, it will be ignored."* — el contenido del evento **nunca se parsea ni se genera**, no hay excepción ni entrada en `syntaxErrors`.
- **Caso real, no hipotético, verificado en el repo actual:** `GmProject/objects/app/app.yy:24-31` tiene 6 eventos habilitados en `eventList`, incluido `{"eventNum":0,"eventType":2,...}` = Alarm 0. `GmProject/objects/app/Alarm_0.gml` existe y contiene `window_center()`. `Object.cpp` no tiene caso para `Alarm_0.gml` (ni genérico ni para `app`), por lo tanto cae en el warning y se descarta. Confirmado con `grep -rn "window_center" CppProject/Generated/*.cpp CppProject/Generated/*.hpp` → **0 resultados**: la llamada a `window_center()` del evento Alarm de `app` no existe en ningún lado del C++ generado actualmente en el repo.
- Confirmado además que esto no es un caso aislado de diseño: en las 58 carpetas de `GmProject/objects/`, la única que tiene archivos de evento fuera de `Create_0`/`Destroy_0` es `app` (`find GmProject/objects -name "*.gml" | grep -v -E "Create_0|Destroy_0"` → solo 5 archivos, todos en `objects/app/`: `Alarm_0`, `Draw_0`, `Other_3`, `Other_62`, `Step_0`). Ningún otro objeto GameMaker del proyecto usa Step/Draw/Alarm/Collision/etc. — toda la lógica de "loop" vive en el objeto singleton `app`.

### Pregunta 3 — noción de plataforma de salida

- `grep -rn "_WIN32|__APPLE__|__linux__|#ifdef|Q_OS"` sobre `CppGen/Sources` → únicos resultados: `CppGen/Sources/Runtime.hpp:772` (`#ifdef _MSC_VER`, para `_dupenv_s` vs `getenv`) y `CppGen/Sources/Runtime.hpp:991` (`#ifdef _WIN32`, para `localtime_s` vs `localtime_r`). Ambos son parte del **runtime propio del ejecutable CppGen** (para poder compilarse y correr en Windows/Mac/Linux como herramienta de build), no tienen relación con el C++ que CppGen emite.
- `CppGen/CMakeLists.txt:4-15,38-46` → ramas `CMAKE_HOST_APPLE`/`WIN32`/`MSVC` configuran cómo se **compila CppGen mismo** (arquitectura de macOS, proyecto de arranque en Visual Studio, flags de warnings), no el código que genera.
- Búsqueda dirigida de literales de plataforma emitidos por el generador (`writeLine("#if...`, `API_OPENGL`, `API_D3D`) dentro de `CppGen/Sources` → **0 resultados**. CppGen nunca escribe una directiva condicional de plataforma en el C++ que produce.
- El repo trae binarios precompilados de CppGen para las 4 combinaciones (`CppGen/Win32/CppGen.exe`, `CppGen/Win64/CppGen.exe`, `CppGen/Mac/CppGen`, `CppGen/Linux/CppGen`), consistente con "la herramienta corre en varios SO, pero genera siempre el mismo C++".
- **Conclusión:** el C++ generado por CppGen es agnóstico de plataforma de salida. Las diferencias de plataforma reales del proyecto (OpenGL vs D3D11, `API_OPENGL`/`API_D3D`) viven exclusivamente en código escrito a mano (`CppProject/Asset/ShaderLoadOpenGL.cpp` vs `ShaderLoadD3D11.cpp`, ya documentado en CLAUDE.md §5), fuera del alcance de CppGen.

### Pregunta 4 — modelo de objetos de GameMaker (instancias, `with`, `other`, herencia)

- `CppGen/Sources/Object.cpp:80` → `CodeWriter::writeLine("struct " + this->name + ": Object");` — **todo objeto GameMaker se convierte en un struct C++ con exactamente un nivel de herencia**, siempre desde la misma clase base `Object` (definida a mano en `CppProject/Asset/Object.hpp:39`). No hay jerarquía de structs que refleje la jerarquía de objetos de GameMaker.
- `CppGen/Sources/Object.cpp` (constructor `Object::Object(String dir)`, líneas 11-61) **nunca lee `parentObjectId` del `.yy`** del objeto. Verificado con `grep -c "parentObjectId" GmProject/objects/*/*.yy` → **15 objetos** de los 58 tienen un `parentObjectId` no nulo en GameMaker (p. ej. `obj_block`, `obj_block_load_element`, etc.), pero CppGen los ignora por completo: no genera herencia C++ entre ellos, ni copia variables/eventos del padre. `grep -rl "event_inherited" GmProject/objects/` → **0 resultados**, así que en la práctica ningún script depende de este mecanismo — pero si alguien lo usara, CppGen no lo soportaría (`event_inherited` no está en `gml.json` `keywords` ni en `functions`, y llamarlo generaría el "FATAL ERROR: Missing function" de `Accessor.cpp:221`).
- `CppGen/Sources/Statement.cpp:607-686` (`WithStatement`) → `with (expr) { ... }` se traduce a una de dos macros, según si `expr` es un nombre de objeto (todas las instancias) o una expresión de id (una instancia):
  - `withAll(Type, otherId)` para `with (obj_tipo)`.
  - `withOne(Type, id, otherId)` para `with (id_expr)`.
- `CppGen/Sources/GML.cpp:61-69` → **CppGen mismo genera la definición de esas macros** dentro de `GmlFunc.hpp` (vía `GML::exportHeader`):
  ```
  #define withOne(type, id, otherId) \
  if (IntType _withSelfId = id) \
  if (IntType _withOtherId = otherId) \
  for (Scope<type> self(_withSelfId, _withOtherId); self.IsValid(); self.Clear())

  #define withAll(type, otherId) \
  if (IntType _withOtherId = otherId) \
  for (Scope<type> self(Object::GetAll(ID_##type), _withOtherId); self.IsValid(); self.NextObject())
  ```
- `CppGen/Sources/Accessor.cpp:530-531` → la keyword `other` se traduce siempre a `self.otherId` — es decir, **`other` nunca es un puntero tipado, es un entero (id de instancia)**. Acceder a una variable vía `other.miembro` termina resolviéndose por el camino genérico de acceso por id (macros `id*`/`idFunc` de `CppProject/Asset/Object.hpp:26-34`, p. ej. `idInt(self.otherId, M_miembro)`), no por acceso directo a struct.
- `CppGen/Sources/Accessor.cpp:250-262` → `id`/`self` se resuelven como "referencia al scope actual"; en `toCpp` (`Accessor.cpp:533-551`) se compilan a `this->id` cuando el código corre dentro de un método de struct fuera de todo `with()` (`thisPtrValid`), a `global::_app->id` si el scope es `app`, o a `self->id` en cualquier otro caso (dentro de un `with()`, usando el `Scope<T> self` local que arma la macro).
- `CppProject/Asset/Scope.hpp:11-61` (hand-written, no generado, pero es la contraparte de las macros de arriba) → `template <typename T> struct Scope` guarda un puntero `T* object` (obtenido resolviendo un id vía `Asset::Find`) y un `IntType otherId`; sobrecarga `operator->()` para que `self->var` funcione como si `self` fuera un puntero. Iterar `with (obj_tipo)` recorre `Object::GetAll(subAssetId)`, un `QHash<IntType, QVector<IntType>>` (`CppProject/Asset/Object.hpp:66`) — es decir, un registro plano de ids por tipo, no una lista enlazada de instancias.
- `CppProject/Asset/Object.hpp:47-57,66-76` → las variables de instancia con tipo resuelto en tiempo de generación se convierten en campos reales del struct C++ (`Object::writeCppHeader`, `Object.cpp:84-86`); las que CppGen no pudo resolver a un tipo único (quedan `Variant`) se acceden dinámicamente vía `GetVarRef`/`dynamicMemberMap` en runtime, con excepción si el tipo choca.
- Confirmado con el mismo `find` de la pregunta 2: de 58 objetos, únicamente `app` usa eventos más allá de Create/Destroy. En la práctica, el "modelo de objetos" que CppGen tiene que resolver es minimalista: casi todos los objetos son bolsas de variables con constructor/destructor; el mecanismo de instancias/`with`/`other` existe para que el código dentro de esos constructores/destructores (y dentro de las funciones de `app`) pueda operar sobre otras instancias.

### Pregunta derivada — por qué "no es de propósito general"

- `CppGen/Sources/Program.cpp:17-22` → exige literalmente una carpeta `GmProject` con al menos un `*.yyp`, y una carpeta de salida fija `CppProject/Generated` (rutas hardcodeadas, no configurables salvo el argumento de raíz del repo).
- `CppGen/Sources/Program.cpp:33,41,50,118` → asume subcarpetas con nombre exacto `sprites`, `shaders`, `scripts`, `objects` dentro de `GmProject`.
- `CppGen/Sources/Program.cpp:125-129` → exige que exista **un objeto llamado exactamente `"app"`**; si no existe, `exit(1)`. Ese mismo objeto es además el único con soporte de eventos extra (Draw/Step/Other_3/Other_62), hardcodeado por nombre literal en `Object.cpp:32`.
- `CppGen/Sources/Object.cpp:38-44` → los números de evento "Other" que sí se reconocen (`Other_3` = fin de juego, `Other_62` = HTTP) son convenciones específicas de Mine-imator, no genéricas de GameMaker.
- `CppGen/Sources/CppGen.hpp:1169` (`Program::varTypeOverride`) → mapa hardcodeado de nombres de variable literales del sistema de importación de bloques de Minecraft de Mine-imator (`build_pos`, `build_pos_x/y/z`, `build_size_x/y/z`, `build_size_xy`, `build_size_total`, `build_single_stateid`, `block_pos_x/y/z`, `blockstartpos`, `blockendpos`) forzados a `Integer` porque el resolver de tipos no los infiere solo.
- `CppGen/Sources/Program.cpp:657-661` → el resolver fuerza el scope de funciones a `"obj_builder_thread"` si su nombre empieza con `block_set_` o `block_tile_entity_` — un prefijo de nomenclatura específico de este proyecto, hardcodeado en el propio C++ de CppGen (no en `gml.json`).
- Sumado a los ~15 nombres de función con lógica especial hardcodeada de la Pregunta 1 (`new_obj`, `array_add`, `ds_map_find_first`, etc.) y a los eventos hardcodeados por nombre exacto de archivo (Pregunta 2), el cuadro es consistente: CppGen no es un compilador de GML genérico con una tabla de símbolos declarativa — es un compilador de **este** proyecto GML específico, con reglas ad hoc de resolución de tipos y de estructura de objetos escritas directamente en su C++ fuente. Mover CppGen a otro proyecto GameMaker requeriría auditar y reescribir estas partes, no solo cambiar `gml.json`.

## Hallazgos

1. **CLAUDE.md §4.3 se confirma en el punto de partida** (`gml.json` lista `constructor/new/delete/static`) pero el subconjunto real es más angosto de lo que sugiere esa lista: sin `try/catch`, sin struct-literal `{}` como expresión, sin funciones anónimas/lambdas, sin interpolación de strings, y `static` solo sirve para métodos de struct (no para variables estáticas locales en funciones sueltas, que sí es sintaxis GML moderna válida).
2. **El manejo de "función desconocida" no es una sola política, son cuatro**, con severidad muy distinta: (a) error léxico/sintáctico → fatal antes de tocar nada; (b) función/tipo desconocido detectado en `resolve()` → fatal antes de escribir; (c) error detectado en `toCpp()` → fatal **a mitad de escribir archivos**, dejando `CppProject/Generated/` en un estado mixto (algunos archivos con la generación nueva, otros con la vieja); (d) un caso puntual (`Accessor.cpp:641`, llamada a función de instancia no encontrada en ningún objeto) que imprime "FATAL ERROR" pero **no aborta y sí emite** una llamada rota (`idFunc(...)`) — el único código real de la herramienta que hace lo que CLAUDE.md pregunta como riesgo ("emite algo roto") sin que el propio `main.cpp` lo detecte como error (no toca `syntaxErrors`, no cambia el código de salida del proceso).
3. **Existe un mecanismo de "función/evento desconocido" completamente distinto y más silencioso todavía**: eventos de objeto GameMaker no reconocidos por nombre de archivo (`Object.cpp:51-59`) se descartan con un simple `WARNING` en consola, sin tocar `syntaxErrors` ni abortar. Se verificó un caso real y actual en el repo: el evento Alarm 0 del objeto `app` (`GmProject/objects/app/Alarm_0.gml`, contiene `window_center()`, habilitado en `app.yy`) no aparece en ningún archivo de `CppProject/Generated/` — su lógica está perdida en el C++ compilado hoy.
4. **El C++ generado es 100% agnóstico de plataforma de salida.** Los únicos `#ifdef` de plataforma en todo `CppGen/Sources` son para que el propio ejecutable CppGen corra en Windows/Mac/Linux como herramienta de build; no hay ninguna rama condicional de plataforma en el código que produce.
5. **El modelo de objetos de GameMaker que CppGen soporta es deliberadamente mínimo, y coincide con lo que el proyecto realmente usa.** Herencia de objetos GameMaker (`parentObjectId`, `event_inherited`) no se soporta ni se necesita hoy (0 usos de `event_inherited`, aunque 15 objetos sí declaran `parentObjectId` en su `.yy` — dato muerto para CppGen). `with`/`self`/`other`/`id`/`noone` se resuelven con un patrón simple y portable: una plantilla `Scope<T>` (puntero + id de "otro") más dos macros (`withAll`/`withOne`) que el propio CppGen escribe en `GmlFunc.hpp`, y un registro plano de ids por tipo de objeto (`Object::GetAll`). No depende de Qt ni de OpenGL — no debería representar riesgo para el port a móvil.
6. **CppGen tiene dos escapes explícitos y ya muy usados para lo que no puede expresar en GML**: `/// CppSeparate <firma>` (71 archivos en `GmProject/`, la función completa se implementa a mano en `CppProject/Gml/`) y `/// CppOnly <línea>` (1 archivo, inyecta una pragma de OpenMP). Esto coincide exactamente con el flujo que describe CLAUDE.md §4.2 para "agregar funcionalidad que GML no tiene" — está confirmado en código, no es solo intención de diseño.
7. **El README no exagera**: hay al menos 6 categorías de asunciones hardcodeadas específicas de Mine-imator dentro del C++ de CppGen (estructura de carpetas fija, objeto `"app"` obligatorio con eventos especiales solo para él, números de evento "Other" con significado propio de este proyecto, lista de nombres de variables del importador de bloques de Minecraft, prefijos de función `block_set_`/`block_tile_entity_`, y ~15 funciones built-in con inferencia de tipo especial por nombre). Portar CppGen a otro proyecto GameMaker implicaría tocar su C++ fuente, no solo `gml.json`.

## Contradicciones con CLAUDE.md

- **§4.1 (diagrama de flujo) y B15 del catálogo de bloqueos (§8)** presentan "CppGen lee `GmProject` → escribe `CppProject/Generated`" como un paso atómico ("se sobreescribe" / "se pierde en el próximo build"). La evidencia (`Program.cpp:190-476`, `Accessor.cpp:808-811`, `CodeWriter.cpp:55-76`) muestra que **no es atómico a nivel de todo el directorio**: cada archivo se escribe con `File::writeAllText` apenas termina de generarse, y un `exit(1)` disparado durante la fase de escritura (posible, ver Hallazgo 2c) deja una mezcla de archivos regenerados y archivos de una corrida anterior. Esto no invalida B15, pero lo matiza: no basta con saber que "editar Generated/ se pierde"; también hay que saber que **una corrida fallida a mitad de camino puede dejar Generated/ en un estado inconsistente que compila pero no corresponde a ningún commit de GmProject**. Vale la pena una nota adicional en §8 o una entrada nueva en el catálogo de bloqueos.
- **La pregunta de §4.3 "¿Falla o emite algo roto?" asume una dicotomía** que la evidencia no sostiene: coexisten cuatro comportamientos (fatal temprano, fatal tardío, fatal-que-no-aborta-y-emite-código-roto, y warning-silencioso-sin-abortar). El caso (d) (`Accessor.cpp:641`) y el caso de eventos ignorados (`Object.cpp:51-59`, con el ejemplo real de `Alarm_0`/`window_center()`) son ambos "emite algo roto/incompleto de forma silenciosa", contradiciendo la lectura optimista implícita en el resto de CLAUDE.md de que CppGen "falla ruidosamente" ante lo desconocido.
- Menor: CLAUDE.md no menciona en ningún lado los mecanismos `/// CppSeparate` / `/// CppOnly`, pese a que son la implementación concreta de lo que §4.2 describe en abstracto ("declarás la función en `gml.json`, la implementás en `CppProject/Gml/`"). En la práctica, `CppSeparate` es un tercer mecanismo (además de `gml.json` + `CppProject/Gml/`) y es el que más se usa (71 archivos) — vale la pena que quede documentado explícitamente en §4.2 para quien tenga que agregar funciones nuevas en Fase 3+.

## Decisión propuesta

**Recomendación para cerrar la tarea 0.2 de Fase 0:**

1. Documentar en CLAUDE.md §4.2 los tres mecanismos reales para agregar funcionalidad (no dos): `gml.json` + `CppProject/Gml/` (funciones simples), `/// CppSeparate` (función entera a mano, 71 usos actuales), `/// CppOnly` (línea de C++ inyectada, 1 uso actual).
2. Agregar una entrada al catálogo de bloqueos (§8) sobre la posibilidad de salida parcial/inconsistente de `CppGen` (ver Contradicciones, primer punto) — severidad baja/media, mitigación: en CI, tras cada corrida de CppGen, verificar que el código de salida del proceso sea 0 **y** que no haya quedado ningún archivo de `Generated/` con timestamp de una corrida anterior (comparar `CodeWriter::totalFilesUpdated` esperado vs. real, o simplemente `git status` sobre `Generated/` tras una corrida limpia).
3. Corregir/instrumentar el caso silencioso de `Accessor.cpp:641`: hacer que ese "FATAL ERROR" realmente llame a `Environment::exit(1)` (como los otros 14 sitios con el mismo prefijo) o, como mínimo, empujarlo a `Program::syntaxErrors` para que afecte el código de salida del proceso (`main.cpp:9`). Alternativa descartada: dejarlo como está confiando en revisión manual del log — ya se demostró que no es confiable, dado que el caso del evento `Alarm_0`/`window_center()` (un descarte silencioso de otra naturaleza, pero de la misma familia de "silencio que compila") pasó desapercibido hasta esta auditoría.
4. Para el modelo de objetos de GameMaker (pregunta 4 de §4.3): **no hace falta un rediseño para mobile.** El patrón `Scope<T>` + `withAll`/`withOne` + registro plano de ids (`Object::GetAll`) ya es C++ puro sin dependencias de Qt/OpenGL, y la herencia de objetos GameMaker no se usa en la práctica (0 `event_inherited`). Alternativa descartada: invertir tiempo de Fase 0 en diseñar un mecanismo de herencia/despacho de eventos más fiel a GameMaker — se descarta porque no hay evidencia de que el proyecto lo necesite hoy, y agregarlo sería trabajo especulativo fuera del alcance medido.
5. Antes de avanzar a Fase 1+, correr CppGen una vez de forma controlada (en una rama, no en `master`) y diffear `CppProject/Generated/` contra el HEAD trackeado, para confirmar si ya existe deriva silenciosa (más allá del caso ya confirmado de `Alarm_0`). Esto no se hizo en esta auditoría por estar fuera del alcance de "auditoría estática" pedido y para no introducir cambios no solicitados en un directorio que CLAUDE.md prohíbe editar manualmente (§2.3) — correrlo sí está permitido (no es "editar"), pero se prefirió dejarlo como una acción explícita y separada, no un efecto colateral de este informe.
